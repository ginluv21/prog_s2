# GDB — Практическое руководство по отладке программ на Си

На основе реальной сессии отладки проекта `prog_s2`.

---

## Теория: как работает отладчик

### Что такое GDB

GDB (GNU Debugger) — отладчик с открытым исходным кодом, входящий в состав GNU toolchain. Он позволяет управлять выполнением другой программы: останавливать её, изучать состояние памяти и регистров, изменять переменные на лету.

### Как GDB управляет процессом — системный вызов ptrace

GDB не встроен в программу. Он управляет ею через системный вызов ядра Linux — **`ptrace`** (process trace). Когда ты запускаешь `gdb ./test.o`, происходит следующее:

1. GDB вызывает `fork()` — создаёт дочерний процесс
2. Дочерний процесс вызывает `ptrace(PTRACE_TRACEME)` — говорит ядру "я хочу быть под контролем"
3. Дочерний процесс вызывает `exec()` — загружает твою программу
4. Ядро останавливает дочерний процесс и уведомляет GDB
5. GDB через `ptrace` может читать/писать память процесса, регистры, управлять выполнением

Именно поэтому GDB требует права на отладку — он работает через привилегированный системный вызов.

### Как работают точки останова (breakpoints)

Программный брейкпоинт работает через инструкцию `INT3` (опкод `0xCC`):

1. GDB запоминает оригинальный байт по адресу брейкпоинта
2. Записывает туда `0xCC` — инструкцию "прерывание"
3. Когда CPU доходит до `0xCC` — процессор генерирует исключение SIGTRAP
4. Ядро уведомляет GDB, GDB останавливает программу
5. GDB восстанавливает оригинальный байт, чтобы программа могла продолжить

Именно поэтому `break datatime_create` — это не просто "пометка", а реальная модификация машинного кода во время выполнения.

### Что такое отладочные символы и флаг -g

Когда компилируешь без `-g`:
```bash
gcc test.c -o test.o
```
Бинарник содержит только машинный код — числа и адреса. GDB видит только адреса (`0x00005555555551a0`), не имена.

С флагом `-g`:
```bash
gcc -g test.c -o test.o
```
Компилятор добавляет в бинарник секцию `.debug_info` в формате **DWARF** (Debugging With Attributed Record Formats). DWARF содержит:
- Соответствие адресов машинного кода → строкам исходного кода
- Имена переменных и их типы
- Имена функций и их параметры
- Структуру вызовов

Именно поэтому GDB знает что адрес `0x55555555e6b0` содержит структуру `datatime` с полями `day`, `month`, `year`.

### Разметка памяти процесса

Каждый процесс Linux видит свою виртуальную память, разделённую на сегменты:

```
Высокие адреса
┌─────────────────────┐
│       СТЕК          │ ← локальные переменные, параметры функций
│   (растёт вниз)     │   адреса вида 0x7fff...
├─────────────────────┤
│         ...         │
├─────────────────────┤
│       КУЧА          │ ← malloc/free, адреса вида 0x5555...e000
│   (растёт вверх)    │
├─────────────────────┤
│    BSS сегмент      │ ← глобальные переменные (неинициализированные)
├─────────────────────┤
│   DATA сегмент      │ ← глобальные переменные (инициализированные)
├─────────────────────┤
│   TEXT сегмент      │ ← машинный код программы
│  (только чтение)    │   адреса вида 0x5555...0000
└─────────────────────┘
Низкие адреса
```

В нашей сессии:
- `dt1 = 0x55555555e6b0` — куча (malloc)
- Стек функции (`dt` внутри `datatime_create`) — временная переменная, исчезает после return

### Что такое стековый фрейм

Каждый вызов функции создаёт **стековый фрейм** — область стека с локальными переменными и адресом возврата:

```
┌──────────────────────────┐  ← вершина стека (RSP)
│  локальные переменные    │    например: int m, unsigned long long total
│  datatime_to_minutes     │
├──────────────────────────┤
│  адрес возврата в main() │
├──────────────────────────┤
│  локальные переменные    │
│  main()                  │    например: dt1, dt2, vec, t
└──────────────────────────┘
```

Команда `bt` (backtrace) показывает все фреймы снизу вверх. `frame N` переключает контекст — поэтому после краша `frame 11` переносит нас в `main()` где объявлен `df`.

### Little-endian: порядок байт

x86-64 использует **little-endian** — младший байт числа хранится по меньшему адресу.

Число 2025 = `0x000007E9`:
```
Адрес:  +0    +1    +2    +3
Байты:  0xE9  0x07  0x00  0x00
```

Поэтому в дампе памяти год 2025 выглядит как `0xe9 0x07 0x00 0x00`, а не `0x00 0x00 0x07 0xe9`.

## 1. Зачем нужен GDB

GDB (GNU Debugger) позволяет:
- Остановить программу в любом месте и посмотреть состояние памяти
- Шагать по коду строка за строкой
- Найти где и почему произошёл краш
- Увидеть реальное содержимое структур в памяти (не то, что думаешь, а то, что есть)

---

## 2. Компиляция с отладочными символами

Без флага `-g` GDB видит только адреса — имена функций, переменных и строки кода недоступны.

```bash
gcc -g test.c lab_2/datatime.c lab_2/bitstruct.c lab_3/contvector.c lab_4/fiovector.c -o test.o
```

Или через Makefile:
```bash
make gcc
```

---

## 3. Запуск GDB

```bash
gdb ./test.o
```

GDB загружает программу но не запускает её — ты сначала расставляешь точки останова.

---

## 4. Точки останова (breakpoints)

Точка останова — это место, где GDB приостановит выполнение программы.

```
break datatime_create    # остановка при каждом вызове datatime_create
break datatime_destroy   # остановка при каждом вызове datatime_destroy
break vec_create         # остановка при создании вектора
break dev_destroy        # остановка при уничтожении device
```

Посмотреть все точки:
```
info breakpoints
```

Отключить точку (например, #1):
```
disable 1
```

В нашей сессии было 4 брейкпоинта. Это позволило поймать каждое создание и уничтожение объекта.

---

## 5. Запуск программы

```
run
```

Программа стартует и останавливается на первой точке останова. Вывод в терминале продолжается до момента остановки.

## 6. Пошаговое выполнение

### `next` — следующая строка

Выполняет текущую строку и переходит к следующей. Если строка — вызов функции, функция выполняется целиком (не заходит внутрь).

```
(gdb) next
27        datatime* dt = malloc(sizeof *dt);
```

### `finish` — выполнить до конца функции

Выполняет всё до `return` текущей функции и возвращает управление вызывающему коду. Показывает возвращаемое значение.

```
(gdb) finish
Run till exit from #0  datatime_create (d=15, m=3, y=2025, h=10, min=30) at lab_2/datatime.c:27
0x0000555555555590 in main () at test.c:23
23        datatime *dt1 = datatime_create(15, 3, 2025, 10, 30);
Value returned is $5 = (datatime *) 0x55555555e6b0
```

**Важно:** после `finish` ты находишься на строке с вызовом функции, но присвоение ещё не выполнено. Надо нажать `next` чтобы `dt1` получил значение.

### `continue` — продолжить до следующего брейкпоинта

```
(gdb) continue
Continuing.
...
Breakpoint 1, datatime_create (d=20, m=5, y=2025, h=18, min=0) at lab_2/datatime.c:27
```

## 7. Просмотр переменных

### `p` — print

```
(gdb) p dt1
$7 = (datatime *) 0x55555555e6b0
```

Показывает адрес указателя. `$7` — это нумерованная история значений в текущей сессии.

```
(gdb) p *dt1
$8 = {day = 15, month = 3, year = 2025, hour = 10, minute = 30, dev = 0x55555555e6e0}
```

Разыменование указателя — видим поля структуры.

**Ловушка:** если `p dt1` возвращает `0x40000` — это мусор, переменная ещё не присвоена. Нажми `next` и повтори.

```
(gdb) p dt1
$6 = (datatime *) 0x40000    ← мусор, присвоение ещё не выполнено
(gdb) next
(gdb) p dt1
$7 = (datatime *) 0x55555555e6b0   ← теперь корректно
```

## 8. Дамп памяти — `x/NxB addr`

Команда `x` (examine) читает сырые байты из памяти.

Синтаксис: `x/<количество><формат><размер> <адрес>`
- `x` — hex
- `b` — byte (1 байт)
- `32` — сколько байт показать

```
(gdb) x/32xb dt1
0x55555555e6b0:    0x0f    0x00    0x00    0x00    0x03    0x00    0x00    0x00
0x55555555e6b8:    0xe9    0x07    0x00    0x00    0x0a    0x00    0x00    0x00
0x55555555e6c0:    0x1e    0x00    0x00    0x00    0x00    0x00    0x00    0x00
0x55555555e6c8:    0xe0    0xe6    0x55    0x55    0x55    0x55    0x00    0x00
```

### Разбор структуры `datatime` (15/03/2025 10:30)

```
Байты 0-3:   0x0f 0x00 0x00 0x00  →  day   = 15   (0x0f = 15)
Байты 4-7:   0x03 0x00 0x00 0x00  →  month =  3
Байты 8-11:  0xe9 0x07 0x00 0x00  →  year  = 2025  (little-endian: 0x07e9 = 2025)
Байты 12-15: 0x0a 0x00 0x00 0x00  →  hour  = 10   (0x0a = 10)
Байты 16-19: 0x1e 0x00 0x00 0x00  →  min   = 30   (0x1e = 30)
Байты 20-23: 0x00 0x00 0x00 0x00  →  padding (выравнивание)
Байты 24-31: 0xe0 0xe6 0x55 0x55 0x55 0x55 0x00 0x00  →  dev* = 0x55555555e6e0
```

Итого: 5 полей `int` (по 4 байта) + 4 байта padding + 8 байт указатель = **32 байта**.

**Little-endian** — байты числа хранятся от младшего к старшему. Год 2025 = `0x07E9`:
- в памяти: `0xe9 0x07` (сначала младший байт `0xe9`, потом старший `0x07`)

### Разбор структуры `vector_t`

```
(gdb) x/32xb vec
0x55555555e750:    0x80    0xe7    0x55    0x55    0x55    0x55    0x00    0x00
0x55555555e758:    0xa0    0xe7    0x55    0x55    0x55    0x55    0x00    0x00
0x55555555e760:    0x00    0x00    0x00    0x00    0x00    0x00    0x00    0x00
0x55555555e768:    0x02    0x00    0x00    0x00    0x00    0x00    0x00    0x00
```

```
Байты 0-7:   0x55555555e780  →  data* (указатель на массив datatime*)
Байты 8-15:  0x55555555e7a0  →  res*  (резервный буфер для роста)
Байты 16-23: 0x00 × 8        →  len   = 0 (вектор пустой)
Байты 24-31: 0x02 0x00...    →  cap   = 2 (ёмкость)
```

### Просмотр `device` (dev)

`dev` лежит по адресу из последних 8 байт `datatime`:

```
(gdb) x/2xb 0x55555555e6e0
0x55555555e6e0:    0x00    0x00
```

`device` — это `uint16_t` (2 байта) с упакованными битами атрибутов устройства. `0x0000` — все атрибуты равны нулю.

## 9. Переиспользование памяти

После уничтожения объекта `unix_start` по адресу `0x55555555e750`, новый `vector_t` был выделен по тому же адресу:

```
Value returned is $10 = (vector_t *) 0x55555555e750
```

Это нормальное поведение — `malloc` переиспользует освобождённые блоки. Означает, что нельзя обращаться к памяти после `free`.

## 10. Стек вызовов — `bt` (backtrace)

После краша программа получает сигнал. `bt` показывает цепочку вызовов от точки краша до `main`.

```
(gdb) bt
#0  __pthread_kill_implementation ...
#1  __pthread_kill_internal ...
#3  __GI_raise (sig=6)                    ← сигнал SIGABRT
#4  __GI_abort ()
#5  __libc_message_impl                   ← вывод сообщения об ошибке
#6  malloc_printerr "free(): double free detected in tcache 2"
#7  _int_free (p=0x55555555e7a0)          ← попытка освободить уже свободный блок
#8  __GI___libc_free (mem=0x55555555e7a0)
#9  dev_destroy (d=0x55555555e7a0) at lab_2/bitstruct.c:24    ← твой код
#10 datatime_destroy (dt=0x55555555e8e0) at lab_2/datatime.c:60
#11 main () at test.c:168                 ← начало цепочки — второй вызов destroy
```

Читай снизу вверх: `main` → `datatime_destroy` → `dev_destroy` → `free` → обнаружен double free → SIGABRT.

---

## 11. Переключение фреймов — `frame N`

После краша GDB показывает системный код (`pthread_kill`). Чтобы перейти в свой код:

```
(gdb) frame 11
#11 0x0000555555555f44 in main () at test.c:168
168        datatime_destroy(df);
(gdb) p df
$1 = (datatime *) 0x55555555e8e0
```

## 12. Демонстрация Double Free

### Что произошло

```c
datatime *df = datatime_create(1, 1, 2001, 0, 0);
datatime_destroy(df);   // первый free — корректно
datatime_destroy(df);   // второй free — КРАШ
```

### Почему `dt = NULL` в destroy не помогает

В `datatime_destroy`:
```c
free(dt);
dt = NULL;  // обнуляет ЛОКАЛЬНУЮ копию указателя
```

`dt` — это параметр функции, копия адреса. Обнуление `dt` не меняет переменную `df` в `main`. После возврата из функции `df` по-прежнему хранит старый адрес.

### Что видит GDB после double free

```
(gdb) p *df
$2 = {day = 48622, month = 21840, year = -1373982890, hour = 1360778612, minute = 0, dev = 0x55555555e7a0}
```

Поля содержат мусор — glibc записал туда свои служебные данные для управления кучей после первого `free`. Но указатель `df` ненулевой, поэтому второй `destroy` не видит проблемы и пытается освободить снова → `SIGABRT`.

## Краткая шпаргалка команд

| Команда | Действие |
|---|---|
| `break <функция>` | поставить точку останова |
| `info breakpoints` | список точек |
| `disable N` | отключить точку N |
| `run` | запустить программу |
| `next` | следующая строка (не заходить в функции) |
| `finish` | выполнить до конца текущей функции |
| `continue` | продолжить до следующего брейкпоинта |
| `p <имя>` | распечатать значение переменной |
| `p *<указатель>` | разыменовать и распечатать |
| `x/32xb <адрес>` | дамп 32 байт памяти в hex |
| `bt` | стек вызовов (после краша) |
| `frame N` | переключиться в фрейм N |
| `quit` | выйти из GDB |
