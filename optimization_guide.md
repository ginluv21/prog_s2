# Влияние оптимизаций компилятора GCC на отладку программ

Исследование на примере проекта `prog_s2`, функция `datatime_to_minutes`.

---

## Теория: компилятор и оптимизации

### Как работает компилятор GCC

Компиляция — это не одно действие, а цепочка из четырёх этапов:

```
исходный код (.c)
        ↓
  1. Препроцессор (cpp)
     — раскрывает #include, #define, #if
     → временный файл .i
        ↓
  2. Компилятор (cc1)
     — разбирает C-код, строит AST (дерево синтаксиса)
     — генерирует промежуточное представление (GIMPLE/RTL)
     — применяет оптимизации
     → файл на языке ассемблера .s
        ↓
  3. Ассемблер (as)
     — преобразует ассемблер в машинный код
     → объектный файл .o
        ↓
  4. Компоновщик (ld)
     — соединяет объектные файлы и библиотеки
     → исполняемый файл
```

Оптимизации применяются на этапе 2 — когда у компилятора есть полная картина кода в виде промежуточного представления.

### Что такое промежуточное представление (IR)

Компилятор не работает напрямую с текстом C или с машинным кодом. Он переводит программу в **промежуточное представление** — внутренний граф вычислений, удобный для анализа и преобразований.

Пример: строка `total += (dt->day - 1) * 24 * 60` в IR превращается в набор элементарных операций: загрузить `dt->day`, вычесть 1, умножить на 1440, прибавить к `total`. Компилятор может переупорядочить, объединить или устранить эти операции.

### Что делает каждый уровень оптимизации

**`-O0` — без оптимизации:**
- Каждая строка C → набор инструкций процессора в том же порядке
- Все переменные хранятся в памяти (стеке), даже если используются один раз
- Код медленный, но отлаживать легко — GDB видит всё

**`-O1` — базовые оптимизации:**
- **Удаление мёртвого кода** — код который никогда не выполняется убирается
- **Свёртка констант** — `2 * 60` вычисляется в compile-time → `120`
- **Распределение регистров** — часто используемые переменные кладутся в регистры CPU вместо памяти
- Строки могут начать "пропадать" при отладке

**`-O2` — агрессивные оптимизации:**
- **Инлайнинг функций** — тело маленькой функции вставляется прямо в место вызова (нет overhead вызова)
- **Объединение вычислений** — несколько операций с одними данными объединяются в одну
- **Устранение общих подвыражений (CSE)** — `a*b` вычисляется один раз если встречается несколько раз
- **Перестановка инструкций** — инструкции переставляются для лучшей загрузки конвейера CPU
- Многие переменные исчезают из отладочной информации

**`-O3` — максимальные оптимизации:**
- **Разворачивание циклов (loop unrolling)** — цикл на N итераций превращается в N копий тела
- **Векторизация (SIMD)** — операции над массивами заменяются на инструкции SSE/AVX, обрабатывающие 4-16 элементов за раз
- **Агрессивный инлайнинг** — инлайнятся даже большие функции
- Код почти не поддаётся отладке

### Почему оптимизации ломают отладку

**Проблема 1: переменные в регистрах**

Без оптимизации переменная `m` хранится на стеке — GDB может прочитать стек и показать значение. С `-O2` компилятор кладёт `m` в регистр `%eax`. GDB видит регистры, но DWARF может не содержать информации о том, что `%eax` сейчас хранит `m`. Результат: `No symbol "m" in current context`.

**Проблема 2: исчезновение строк**

Строки 386 (`total = 0`) и 396-397 были удалены — компилятор вычислил их результат заранее и встроил в другие инструкции. В бинарнике нет инструкций соответствующих этим строкам → поставить брейкпоинт на них невозможно.

**Проблема 3: нотация `@entry`**

```
datatime_to_minutes (dt=dt@entry=0x55555555d940)
```

`@entry` означает: компилятор переиспользовал регистр, в котором был `dt`, для других нужд. GDB запомнил значение при входе в функцию (`@entry`), но текущее значение регистра уже другое.

**Проблема 4: порядок выполнения**

С `-O2` CPU может выполнять инструкции не в том порядке, что написан в коде (out-of-order execution + compiler reordering). При пошаговом выполнении курсор в GDB "прыгает" непредсказуемо.

### Флаг `-Og` — оптимизация для отладки

Специальный уровень, появившийся в GCC 4.8:
```bash
gcc -Og -g test.c -o test.o
```
Применяет оптимизации которые не мешают отладке: убирает мёртвый код, но не переставляет инструкции и не убирает переменные. Компромисс между скоростью и читаемостью при отладке.

### Почему I/O-bound код плохо оптимизируется

Компилятор оптимизирует **вычисления** — арифметику, логику, ветвления. Но системные вызовы (`write`, `read`, `open`) — это обращения к ядру, компилятор не может их ускорить или устранить.

Наш проект тратит 90%+ времени на `fread`/`fwrite`/`fprintf` → оптимизации дают только 5-10% ускорения. В вычислительно интенсивном коде (обработка изображений, численные методы) `-O2` даёт 2-5x ускорение.

## 1. Что такое уровни оптимизации

GCC поддерживает несколько уровней оптимизации:

| Флаг | Описание |
|---|---|
| `-O0` | Без оптимизации (по умолчанию). Код один в один соответствует исходнику. |
| `-O1` | Базовые оптимизации: убирает мёртвый код, упрощает выражения. |
| `-O2` | Агрессивные оптимизации: инлайнинг функций, объединение вычислений, перестановка строк. |
| `-O3` | Максимальные оптимизации: разворачивание циклов, векторизация. |

Флаг `-g` добавляет отладочные символы и не конфликтует с оптимизациями — можно использовать вместе: `gcc -O2 -g`.

## 2. Компиляция и замер времени

```bash
gcc -g    test.c ... -o test.o      # без оптимизации
gcc -O1 -g test.c ... -o test_O1.o
gcc -O2 -g test.c ... -o test_O2.o
gcc -O3 -g test.c ... -o test_O3.o
```

### Результаты (1 000 000 элементов)

| Операция | O0 (нет) | O1 | O2 | O3 |
|---|---|---|---|---|
| Генерация | ~340 мс | 337 мс | 329 мс | 333 мс |
| save txt | ~490 мс | 486 мс | 476 мс | 473 мс |
| save bin | ~70 мс | 67 мс | 75 мс | 68 мс |
| count txt (slow) | ~460 мс | 456 мс | 448 мс | 444 мс |
| load_vec_txt | ~490 мс | 492 мс | 492 мс | 490 мс |
| load_vec_bin | ~85 мс | 82 мс | 85 мс | 79 мс |

**Вывод по производительности:** разница минимальная (5-10%). Причина — узкое место в операциях ввода-вывода (`fread`/`fwrite`/`fprintf`). Это системные вызовы, компилятор их не оптимизирует. Оптимизации дают ощутимый эффект только в вычислительно интенсивном коде.

## 3. Исследуемый код — `datatime_to_minutes`

Функция содержит цикл и несколько сложений — хороший кандидат для наблюдения за оптимизациями.

```c
// lab_2/datatime.c
unsigned long long datatime_to_minutes(const datatime *dt) {
    if (dt == NULL) {                                          // строка 382
        return 0;
    }
    unsigned long long total = 0;                              // строка 386
    total += (unsigned long long)dt->year * 365 * 24 * 60;    // строка 389
    for (int m = 0; m < dt->month - 1; m++) {                 // строка 392
        total += month_lengths[m] * 24 * 60;                  // строка 393
    }
    total += (dt->day - 1) * 24 * 60;                         // строка 396
    total += dt->hour * 60;                                    // строка 397
    total += dt->minute;                                       // строка 398
    return total;                                              // строка 400
}
```

Тест вызывает функцию 4 раза в цикле:
```c
for (int i = 0; i < 4; i++) {
    unsigned long long mins = datatime_to_minutes(dates[i]);
    ...
}
```

## 6. Сравнение: какие строки исчезли

| Строка | Код | O0 | O2 |
|---|---|---|---|
| 386 | `unsigned long long total = 0;` | видна | **исчезла** |
| 389 | `total += year * 365 * 24 * 60` | видна | видна |
| 392-393 | цикл по месяцам | видна | видна |
| 396 | `total += (day-1) * 24 * 60` | видна | **исчезла** |
| 397 | `total += hour * 60` | видна | **исчезла** |
| 398 | `total += minute` | видна | видна |
| 400 | `return total` | видна | видна |

Компилятор:
- Строку 386 (`total = 0`) слил с первым использованием `total` на строке 389
- Строки 396 и 397 объединил в одно выражение — в бинарнике отдельных инструкций нет

## 7. Проблемы при отладке оптимизированного кода

### 7.1 Переменная недоступна после цикла

В O0 `m` недоступна после `for` — это нормально (вышла из области видимости). Но в O2 это же происходит и `внутри` цикла для некоторых промежуточных переменных:

```
(gdb) p m
No symbol "m" in current context.
```

### 7.2 Брейкпоинт на удалённую строку не срабатывает

Строки 396-397 исчезли из бинарника. Если попытаться поставить брейкпоинт:

```
(gdb) break datatime.c:396
```

GDB поставит его на ближайшую существующую строку — поведение непредсказуемо.

### 7.3 Параметры помечаются `@entry`

```
# O0:
datatime_to_minutes (dt=0x55555555e750)

# O2:
datatime_to_minutes (dt=dt@entry=0x55555555d940)
```

`@entry` означает: компилятор мог переиспользовать регистр с `dt` для другой цели. GDB показывает значение на входе в функцию, но не гарантирует что `dt` сейчас в том же регистре.

### 7.4 Код выполняется не в том порядке, что написан

Компилятор переставляет инструкции. При пошаговом выполнении курсор в GDB может "прыгать" — это дезориентирует при отладке.

## 8. Выводы

1. **Оптимизации ускоряют код** — но в данном проекте эффект минимален (5-10%), так как узкое место — ввод-вывод, а не вычисления.

2. **Оптимизации разрушают отладку** — исчезают строки, переменные, нарушается порядок выполнения.

3. **Для отладки используй `-O0`** или специальный флаг `-Og` (оптимизация без ущерба для отладочной информации).

4. **Для продакшена используй `-O2`** — стандартный баланс скорости и предсказуемости.

5. **`-O3` не всегда быстрее `-O2`** — результаты в таблице подтверждают это: разница в пределах погрешности измерений.

6. **GDB + `-g` работают с любым уровнем оптимизации** — но чем выше уровень, тем меньше информации доступно при отладке.
